Workflows & patterns

How a new enterprise problem is decomposed into a workflow, then given exactly the controls its worst case demands. Every flow below is real in agent/graph.py; the framing is workflows/PATTERNS.md.
The two axes. The shape comes from one question — is the path known before we start? The controls come from another — what must not go wrong at this step? Shape is a design choice; controls are non-negotiable per the step's risk.

The determination method — how the pattern was chosen

  1. Is the path known before starting, or does it depend on findings? Known ahead → it's a workflow (go to 2). Depends on what you discover mid-task → it's a dynamic agent (go to 3).
  2. If the path is known — what shape? One thing after another → prompt-chaining. It splits by request type → routing. Independent pieces, no ordering → parallelization (for speed, or vote for reliability).
  3. If the path is dynamic — how does it progress? Sub-tasks it can't enumerate up front, farmed out and reassembled → orchestrator-workers. A draft improved against a checkable standard → evaluator-optimizer.
  4. Then, per step: "what must-not-go-wrong here?" — that answer attaches the tools and controls. A step that acts → an approval gate (HITL) + deterministic authz. A step that retrieves customer data → tenant/clearance filter before ranking + injection-inert. A step that answers → grounding + egress PII redaction.
Plain statement: steps 1–3 give the shape; step 4 (risk-per-step) gives the controls. Decompose into a workflow, then give each step exactly the guards its worst case demands — nothing more, nothing less.

A dynamic agent (ReAct) is the other axis (PATTERNS.md §1): the path is determined at runtime — the model plans, acts, observes, and adjusts, bounded by budgets and traces.
