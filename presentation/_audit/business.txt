Agent Scoping Brief — Procurement Operations
Agent Scoping Brief · Working Backwards · Scope Before Code
Procurement operations: what earns an agent, and what doesn't
The outcome, stated first
An employee asks "can I buy this, and how do I get it approved?" and gets a correct, policy-grounded answer in seconds. When the request commits money, a human approves exactly what the agent proposed — nothing altered after they click — and the decision leaves an audit-proof record. Cycle time drops from days to minutes; not one dollar moves without an authorized, approved, tamper-evident decision.
Act 1 · Hypothesis Decompose the problem, and use three numbers to decide what earns an agent — before writing code.
Act 2 · Evidence Run the reference agent. Check each hypothesis against real telemetry and eval data — including one surprise.
Act 3 · Next From what held and what surprised us, decide what to harden next — and what we deliberately deferred.
01 The business problem
Every purchase at a company runs the same gauntlet. An employee needs to buy something, has to find out if they're allowed to, has to get it approved by the right person, and finance needs the whole thing to be correct and auditable . Today most of that is manual — and the manual parts are both the slow parts and the risky parts.
step 1 Employee asks "Can I buy this software? Who has to approve it?"
step 2 Find the rule Someone digs through policy docs for the limit and the vendor status.
step 3 Get approval A manager signs off — often without seeing whether it even passed policy.
step 4 Commit the money A PO is raised. This step is irreversible and audited.
It's slow Policy lookups and approval chases turn a two-minute decision into a two-day one.
It's risky Approvers rubber-stamp; off-policy and duplicate spend slips through; the money step has the least scrutiny.
02 How we prioritize — the numbers behind each call Act 1 · hypothesis
We don't guess what to automate. We score each layer of the problem on three numbers , then apply one rule. The scores are our hypotheses — stated before we build, so the run in Act 2 can confirm or overturn them.
the rule An agent earns its place only where the work is reasoning over messy, unstructured input (like reading policy documents to answer a question). Anything with a fixed, exact answer — a lookup, a threshold check, a routing rule — belongs in ordinary code, which is cheaper, faster, and can't be talked into the wrong answer.

03 Why this is worth solving now
The bottleneck is human attention spent on the wrong things.
Today, people spend their scarce attention on policy lookup (answerable from documents) and on rubber-stamping requests a fixed rule could have cleared or blocked. The one decision that actually needs human judgment — "should we commit this money?" — gets the least attention because it's buried under routine.
The agent inverts that: automate the comprehension and the eligibility checks so a human is pulled in only for the genuinely discretionary, money-committing call — and when they are, they approve something that already passed authorization and can't be altered after they click. Fewer approvals, each one meaningful, each one tamper-evident. That's a workflow-integrity win before it's an AI win.
04 What we'll measure to know it worked Act 1 · success criteria
These are the success criteria for the hypotheses above — defined before code. Two classes, and they're not equal. Invariants must be exactly zero — they're integrity guarantees, not averages to optimize. Quality and cost are graded. Values marked REF are already measured on the reference implementation (the IT-ops agent that proves this framework); procurement's own numbers get set in a pilot.
North star the one number that means it's working
Autonomous resolution rate Share of eligible requests finished end-to-end with zero governance breaches . A resolution that breached doesn't count — the two are inseparable. target ≥ 60% pilot
Invariant guardrails must be exactly 0 — these gate the release
Authorization breaches Any action that ran when the rule should have blocked it. must = 0 0 REF
Mutated executions Any action that ran different from what the human approved. must = 0 0 REF
Cross-department leaks Any data or action crossing a department boundary. must = 0 0 REF
Injection-containment failures Any hidden instruction in a document that reaches a real action. must = 0 0 REF
Quality graded against thresholds
Retrieval recall@k Did it pull the right policy text to answer from? ≥ 0.70 1.00 REF
Groundedness Every claim traces to a citation; no made-up answers. = 1.00 1.00 REF
Plan efficiency Useful steps ÷ total — no wandering. ≥ 0.80 nightly
Operational cost & load
Cost / resolved request Tokens × rate per request. Route cheap reads to cheap surfaces. track $0.013–0.038 REF
Latency / resolved request End-to-end time per request. track 5.6–17.3s REF
Human-approval load How often a human is pulled in. Too high = agent isn't earning its keep; too low = under-gating. tune pilot
05 What we found when we ran it Act 2 · evidence
We ran the reference agent through the real scenarios and the adversarial suite, and checked each hypothesis against actual data. Three held; one surprised us — and the surprise is the most useful thing here, because it's the kind of defect you only find by measuring, not by reasoning.
06 The agent this becomes from scoping to build
The hypotheses and the evidence point at one thing to build: a governed agent for the two layers that earned it — grounded policy answers, and a gated PO-approval action. Everything the triage flagged as code, query, workflow, or BI becomes a tool the agent calls , not agent reasoning. Here's the bare-minimum shape — and where it continues.
what we're building
A governed procurement agent : grounded policy Q&A over the policy corpus (RAG), plus a human-approved, tamper-evident PO submission — on a deterministic control plane, behind an eval gate, with per-layer telemetry on every run.
the loop · what runs, in what order
guard_input M →
plan M →
act M ⇄
tools M →
authorize C →
approval_gate C →
execute C →
finalize M
M = model nodes (reason, can be swayed) · C = code nodes (deterministic gates that enforce). The authorize→gate order is the D-045 fix: a disallowed action never reaches a human.

07 Where agents fail — and how we catch it
The findings above were possible because we designed for the ways agents actually break. These aren't "the AI made something up" — they're the classic failures of letting an unpredictable component near an irreversible action. Each has a fix that lives outside the model, and each is caught by a test or by telemetry, not by hoping.
08 What we're not building now — and the path if we did Act 3 · next
Scope is a decision, not an accident. Each item below is a real production control with a known shape; deferring it is a judgment about the three-hour budget. A human already sees the exact action and its destination before anything fires, so nothing here is a hole in the demo — they're hardening for regulated scale.
Deferred control Sev / effort Why deferred · what closes it
Authenticate the approver (IdP at the gateway) S2 · M Today the fingerprint binds what is approved, not who approves. Production verifies an identity token so approval authority is authenticated too. I built the first control, documented the second.
Destination allowlist (data-loss prevention) S2 · L The rules gate whether a tool runs, not where its output goes. A destination allowlist is the next control for regulated data. A human still sees the destination first.
Tamper-evident compliance log S2 · M Tracing today is for debugging , not a permanent who-approved-what ledger. First item for an audited deployment.
Look-alike identity characters S3 · M We fold case/spacing/width look-alikes; full cross-alphabet needs a specialized library. Low severity because identity comes from a verified login — tracked openly, not hidden.
Model bake-off numbers RUN Swapping the model is trivial here; the same scenarios run through Claude, an open-weight model, and OpenAI. The point isn't which model wins — it's that every guardrail holds identically regardless. Numbers captured on a provisioned run.
— Plain-English glossary
Reference implementation: governed IT-ops agent · LangGraph + Bedrock (open & closed weights) + Anthropic API · deterministic control plane · per-layer telemetry · eval gate (invariant breaches = 0).
REF values are measured on that implementation; procurement targets are set for a pilot. The framework stays fixed — the four domain slots (golden set, corpus, tools, output contract) are what change per customer.
