🛡️ L1 Guardrails (6 layers)
▾
What Layered input/output safety: regex PII+injection, Presidio, Prompt-Guard/Lakera, Bedrock Guardrails, output grounding, HITL.
Why this choice Deterministic where possible (free, fast, testable), model-judged only where necessary, humans on the residual. Each layer is a tested invariant, not a prompt.
Alternatives considered LLM-judge-everything (slow, non-deterministic, costly) · a single vendor guardrail (vendor lock, misses tool-level risks) · no guardrails (unshippable).

🔎 L2 Routed Retrieval
▾
What Provenance per chunk; tenant + 4-tier sensitivity + source filters applied BEFORE ranking; hybrid BM25+embeddings; ids are the only legal citations.

Alternatives considered Score-then-filter (leakable) · single-tenant index per customer (cost, ops) · pure vector search (misses exact ids/SKUs; no clearance model).

🧠 L3 Agentic Memory (3 kinds)
▾
What Short-term (checkpointed thread), long-term semantic + episodic (tenant+user scoped, injected before planning, approval-gated writes, TTL, forget()).

🔧 L4 Tools & Human-in-the-Loop
▾
What 9 tools: read (search/lookup/recall/calc) with no approval; action (reset_access/create_ticket/provision/remember/escalate) gated through a human approval node.
Why this choice An agent that answers is useful; one that ACTS is valuable — but every side effect must be human-approved. Unknown tool -> approval by default; strict mode raises on drift.
Alternatives considered Read-only agent (no real work) · auto-execute actions (dangerous) · approve-everything (useless friction).

⚖️ L5 Model Selection (open vs closed)
▾
What Constraint-driven registry: select_model(task, residency, cost, quality, license). Anthropic API + Bedrock (Claude closed; Qwen/Llama open, in-account) + HF. Fine-tune path via LoRA + Bedrock Custom Model Import.
Why this choice The governance layer bounds worst-case behavior INDEPENDENT of model choice — the deterministic controls run outside the model and hold across Claude/Qwen/Llama — so model selection is a pure quality/cost/residency decision, not a safety one. Alternatives considered One hardcoded model (no residency story) · always-open (quality risk on reasoning) · always-closed (cost, lock-in, no in-account option for regulated data).

🔌 L8 MCP Integration
▾
What Expose the agent&#x27;s READ tools to MCP clients (Claude Desktop, IDEs, other agents) and consume customer MCP servers — everything flows through the SAME guards + HITL. Published set is derived from the tool registry; action tools are never exposed.
Why this choice MCP hands tools to a client we don&#x27;t govern, so only reads (tenant/clearance-scoped inside themselves) are safe to publish. A side effect is a decision — it stays behind the approval node. The server refuses to boot if an action tool ever looks read-only (fail loud).
Alternatives considered Expose all tools over MCP (a client could fire side effects unapproved) · a bespoke non-standard API (no interop) · no MCP (agent can&#x27;t compose with the customer&#x27;s other agents).

Governed by D-025 MCP server publishes READ tools ONLY; the 5 action tools are never exposed and stay behind ✓ tests/test_mcp.py
🧩 L9 Vector Backend (swappable)
▾
What The retrieval contract search(query, tenant, sensitivity, k) is backend-swappable: in-memory BM25 by default (zero-setup), Pinecone via VECTOR_BACKEND=pinecone — namespace-per-tenant, sensitivity as a query-time metadata filter. Callers never branch on the backend.
Why this choice Meet the customer&#x27;s data where it already lives (Pinecone/Databricks/Snowflake/pgvector) without changing the agent. Tenant isolation stays structural (a query hits ONE namespace); the contract is the seam, so the store is a config choice, not a rewrite.
Alternatives considered Hardcode one vector DB (rewrite per customer) · move customer data into our store (residency/governance nightmare) · post-hoc filtering (leakable, not structural).
Evidence (from latest eval: bake-claude)
default backend (zero-setup) in-memory ✓ VECTOR_BACKEND=pinecone → PineconeIndex yes ✓ search() contract identical across backends yes ✓

🚀 L10 Infra / Deployment
▾
What deploy/ ships three runnable paths: Dockerfile (container/App Runner), template.yaml (AWS SAM → Lambda), hf_endpoint.py (HF Inference Endpoint for open weights). Bedrock runs models in-account for residency.
Why this choice Forward-deployed means it has to RUN in the customer&#x27;s environment in hours, inside their compliance boundary. Serverless for the API, in-account Bedrock for regulated inference, self-hosted HF for open weights — the residency story is backed by real deploy artifacts, not a diagram.
Alternatives considered A notebook demo (never ships) · one cloud only (no residency options) · vendor API only (no in-account path for regulated data).
